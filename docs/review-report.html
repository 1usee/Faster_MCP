1　已修复的实质缺陷

已修复 registry.py _collect_tools 重复收集，导致工具重复注册

这是最严重的一个。_collect_tools 里存在两段功能重叠的代码： 前半段已经把显式声明的工具收进 specs，函数末尾又出现了一段"合并显式声明工具"的旧逻辑， 再次调用 feature.tools() 做同样的合并。

后果有两层：一、feature.tools() 每个功能被调用两次（若有副作用会翻倍）； 二、后段逻辑用 declared_names = {s.name for s in specs} 去重， 而 specs 里已经有这些名字，于是后段几乎全部被 continue 跳过—— 看起来"没出错"，实际上是一段永远不会产生正确效果的僵尸代码，掩盖了前段逻辑的真实行为。

删除函数末尾整段重复的 try/except + declared_names 逻辑， 只保留前半段"显式优先 + replace() 派生副本"的版本。

已修复 loader.py 拓扑排序把 None 塞进结果列表

_sort_by_dependencies 的收尾循环写成 for name in ...: visit(name, [])， 漏了对返回值的处理。而 visit 在遇到"已完成"节点时会执行 return（返回 None）。

具体触发路径：先排序 test_c → test_b → test_a，visit("test_a") 把三者依次标记为 已完成并 append；回到外层循环处理 test_b 时 state["test_b"] == 2，走 return。 虽然 ordered 是靠 append 累加、None 不会进列表， 但这段代码的语义是错的——它依赖"return 恰好不 append"这个隐含巧合才正确。 一旦将来有人把 visit 改成 return ordered.append(...) 式的写法，立刻静默出错。

收尾循环加 if state[name] == 0: 判断，让意图显式化，不再依赖巧合。

已修复 registry.py _declared_tools 是死代码，与文档不符

Feature._declared_tools 的注释写着"装饰器登记下来的工具，按声明顺序保存"， tools() 的默认实现写着 return list(self._declared_tools)， __init_subclass__ 还专门为每个子类重置这个列表。

但通读全项目后发现：装饰器只设置了 __mcp_tool__ 属性，从来不往 _declared_tools 里追加任何东西。 也就是说 _declared_tools 永远是空列表，tools() 永远返回 []， __init_subclass__ 在做无用功。更麻烦的是 _collect_tools 里那句注释 "tools() 的默认实现返回的就是装饰器登记结果"——这句话是错的， 它会让后续维护者基于错误假设去改代码。

真正的收集路径是：registry 扫描实例属性上的 __mcp_tool__ 元数据。 tools() 只服务于"显式声明"这一种风格。
把三处文档改成与实现一致，tools() 默认返回 [] 并说明装饰器风格不经过它。

已修复 registry.py 显式声明的 ToolSpec 被就地改写

旧代码在合并显式工具时执行 spec.feature_name = feature.name， 这是就地修改调用方传进来的对象。如果某个功能的 tools() 返回模块级常量列表 或缓存对象，同一批 ToolSpec 会被反复改写；一旦被两个注册表实例使用，字段值会互相污染。

改用 dataclasses.replace() 派生副本，并加了"重复声明同名工具"的显式报错。

2　建议修改（已全部完成）

以下 9 项已在后续处理中全部改进，并配上了回归测试。每项保留原分析， 末尾用已处理说明改动内容。

高 safe_eval.py _normalize_numeric 会削掉非整数浮点的精度

该函数把浮点结果 round(value, 12)，目的是收敛 0.1+0.2 这类尾部噪声。 对整数形式的浮点（2.0）和近整数是好事，但对真正的无限小数会损失有效数字：

1/3  → 0.333333333333   （应有 16~17 位有效数字，实际只剩 12 位）
pi   → 3.14159265359   （math.pi 本可精确到 3.141592653589793）

对一个"主打精确计算"的工具来说，把 pi 的精度砍掉 5 位是自相矛盾的—— 用户用这个工具就是为了避免模型自己瞎猜，结果工具本身给了近似值。

现有测试 test_constants 用的是 pytest.approx(math.pi)， 相对容差默认 1e-6，12 位精度照样能过，所以测试不会报警。这是测试的盲区。
建议把"收敛噪声"和"保留精度"分开处理：只对绝对值接近某个整数的浮点做取整， 其余原样返回。或者把容差从 abs_tol=1e-12 收紧到 1e-15， 并把展示层的 12 位截断继续留在 engine.format_value（那里只影响显示、不影响 raw_value）。 同时给 pi、1/3 加一条"高精度不被削"的测试。

已处理 _normalize_numeric 改为双条件判定： 相对误差 < 1e-15（约一个双精度 ulp）且收敛后表示更短，才采纳收敛值。 pi、1/3、sin(1) 现在都保持全精度。 新增 6 条精确断言（用 == 而非 approx）守住这个行为。

高 engine.py 体积单位里 m3 / cm3 的语义有歧义

volume 表的基准单位是升，但键名写的是 m3、cm3—— 这两个符号读起来像立方米/立方厘米，而 1 m³ = 1000 L 的系数也确实按立方米算。 问题是模型很可能把 m3 理解成别的东西，也可能传 m^3、m³、立方米： 立方米 有中文别名但 m³ / m^3 都没有。

数值本身是对的（1 m³ = 1000 L ✓，1 cm³ = 0.001 L = 1 mL ✓），隐患在于可输入性。

补 m^3、m³、cm^3、cm³ 等写法到别名表。 另外 _normalize_unit 里的 .replace("°","") 顺带能处理 °c， 但幂符号 ³ 不会被处理——这是两个独立的规范化需求。

已处理 补齐了 m^3 / m³ / cm^3 / cm³ / mm³ 及对应中文写法， 并新增 3 组共 9 条别名换算测试（含 m³ → cm³ 往返）。

高 docs/EXTENDING.md 与 docs/ARCHITECTURE.md 有失效引用

通读发现两处文档与代码现状不一致：

  • EXTENDING.md 第 1.3 节的三层分工表里，把 safe_eval.py 写成"底层"， 但计算器的实际布局是 feature.py / engine.py / safe_eval.py，表格没体现 engine 这一层；
  • ARCHITECTURE.md 的时序图里提到 registry.finalize() 会做"至少一个功能"的校验， 但没说清 build_server 里 load_features 返回的是全局单例还是新实例—— 这个细节在读者想写测试时很关键。
这两处属于"文档与实现细微脱节"，不影响运行。建议在下次改文档时顺手对齐， 不要单独为它们发起一次修改。

已处理 EXTENDING.md 三层分工表已改为直接用计算器的 feature.py / engine.py / safe_eval.py 举例；ARCHITECTURE.md 时序图补注了 load_features 的返回值与 target= 参数的用途。

中 server.py 包装壳依赖 __signature__，各 SDK 版本行为不一致

_make_wrapper 用 wrapper.__signature__ = signature 把原签名挂到壳上， 让 MCP SDK 据此生成 inputSchema。这个手法在 Python 层面是有效的，但是否被 SDK 采纳取决于它怎么读签名： 有的版本用 inspect.signature(fn)（会尊重 __signature__）， 有的版本用 fn.__code__.co_varnames（不会尊重）。

如果是后者，模型看到的 calculate 参数会变成 *args / **kwargs， 参数说明全部丢失——工具仍然能调，但模型不知道要传 expression。

这也是 pyproject.toml 里把 mcp 锁在 <2 的原因之一。 但锁定不等于验证过。
跑通 python -m faster_mcp --list 后，用真实客户端连一次， 确认工具面板里 calculate 的参数显示为 expression (string) 而不是 kwargs。 若显示不对，改用 functools.wraps + 显式 __code__ 伪造，或直接为每个工具生成独立函数。

已处理（部分） 代码层面无法在不引入风险的前提下确定性地绕开各版本差异， 所以保留现有写法，但已在报告第 0 节把它列为验证清单的头号检查项。 这一项必须靠真实运行确认，不是改代码能解决的。

中 safe_eval.py 布尔字面量的处理顺序有隐患

visit_Constant 里先判断 isinstance(value, bool) 再判断 isinstance(value, (int, float))， 顺序是正确的（因为 Python 里 bool 是 int 的子类，顺序反了会把 True 当数字 1）。 但同样的陷阱在另外两个地方没有防护：

  • _as_seq 执行 [float(v) for v in values]，True 会静默变成 1.0；
  • convert() 的入参校验写了 isinstance(value, bool) 排除布尔，处理是对的， 但表达式路径 mean(True, False) 会走 _as_seq 绕过去。
在 _as_seq 里加一条布尔检查并抛 ToolInputError， 与 convert() 的处理保持一致。低风险，但能把"数字函数收到布尔"这件模糊的事变明确。

已处理 _as_seq 现在显式拒绝 bool 与非数字类型， 并新增 3 条测试（mean(True, False)、sum(1, True)、mean([True, 1]) 均报错）。

中 smoke_test.py 与 tests/ 的断言有重复盲区

三份测试加起来覆盖面不错，但都漏了同一类问题：没有任何测试检查 raw_value 的精度。 test_calculator.py 检查 raw_value == approx(339.0)，用 approx 就等于放弃了精度断言。 再叠加第 2 节提到的 _normalize_numeric 问题，精度退化会一路通过所有测试。

加一条不含 approx 的精度断言，例如 assert feature.calculate("pi")["raw_value"] == math.pi（精确相等）， 以及 assert feature.calculate("1/3")["raw_value"] == 1/3。这类断言最能守住"精确计算"这个卖点。

已处理 新增 test_raw_value_keeps_full_precision， 对 pi / 1/3 / 2/7 / sin(1) 的 raw_value 做精确相等断言； test_calculate_returns_structured_payload 里的 approx 也已去掉。

中 pyproject.toml 依赖上限的策略值得再确认

依赖写成 mcp>=1.2,<2。理由是已确认官方 SDK v2 已发布，锁在 1.x 更稳。 这是刻意的保守选择，本身没错，但有个副作用：

pip install -r requirements.txt 会装上 1.x 最新版，而这个版本号范围从未被真实验证过。 如果 1.28 之类的版本改了 FastMCP.add_tool 的签名，mount_tools 会立刻失败。

要么把范围收紧到"实际验证过的那个小版本"，要么在 README 里明确写"已验证版本：mcp==x.y.z"。 requirements.txt 目前只有宽范围，改成带注释的精确版本更可信。

已处理 requirements.txt 与 README 都补上了版本策略说明， 明确告知"宽范围只避免冲突、不保证可复现"，并给出改成精确版本的具体指引。 实际锁定哪个版本仍需走完第 0 节的验证。

中 safe_eval.py describe_capabilities 的函数清单是手写的，会漂移

describe_capabilities() 里把函数按"基础/幂与根/对数…"分类手写了一遍， 而真正的实现是 SAFE_FUNCTIONS 字典。两者是独立维护的：

加了新函数到 SAFE_FUNCTIONS 但忘了更新 describe_capabilities， 模型查询能力时会查不到那个函数，从而不敢用——这个工具存在的意义（让模型先查后用）就被破坏了。

加一条测试：从 SAFE_FUNCTIONS 取出所有键， 断言它们都出现在 describe_capabilities()["functions"] 的某个分类里。 这类"两份数据必须同步"的约束，用测试守最省心。

已处理 新增 test_describe_capabilities_lists_every_safe_function， 双向断言函数清单与 SAFE_FUNCTIONS 完全一致（多一个少一个都失败）， 并另加一条常量同步测试。

低 config.py 环境变量没有类型校验

Settings.from_env 读 FASTER_MCP_LOG_LEVEL 时只做 .upper()， 非法值（如 "VERBOSE"）不会报错。好在 setup_logging 里用了 getattr(logging, level, logging.INFO) 兜底，所以不会崩，只是静默退回 INFO。

同样 FASTER_MCP_NAME 传空串会得到空的服务名，客户端里显示为空。

可选。加一个 __post_init__ 校验并在非法时 warning， 让配置错误可见而不是静默降级。优先级低，因为不会造成实际故障。

已处理 Settings 新增 __post_init__： 空服务名回退为默认值，非法日志级别回退为 INFO，两者都发 warning。 新增 4 条配置测试。

低 engine.py _collect_values 吞掉所有异常

收集中间变量时用了 except Exception: break。作为"辅助信息"的容错这可以理解， 但它连 KeyboardInterrupt 之外的编程错误（如 NameError）也一起吞了。 如果将来 _eval_one 因为内部 bug 抛错，主计算会正常返回、变量列表悄悄为空，问题被藏起来。

收紧为 except ToolInputError: break， 让非预期的异常继续抛出去。异常处理的粒度应当尽量精确。

已处理 已收紧为 except ToolInputError。 变量收集是辅助功能，只该吞"预料之内"的输入错误，程序 bug 应照常暴露。

低 safe_eval.py MAX_INT_DIGITS 定义后未被使用

常量表里定义了 MAX_INT_DIGITS = 4300 并注释"Python 3.11+ 默认上限"， 但通读全文找不到任何地方引用它。实际生效的整数限制是 MAX_NUMS_IN_LITERAL（限制字面量） 和 Python 自身的 int→str 转换上限（限制输出）。

要么删掉它，要么在 compute() 里对超大整数结果主动做检查并给出友好提示 （当前如果结果超过 4300 位，会在 format_value 的 str(value) 处抛 ValueError: Exceeds the limit for integer string conversion——这是一个未被捕获的异常路径）。

已处理 format_value 现在先估算十进制位数， 超限则返回"超大整数"提示而非抛异常；compute() 同步给出 log10() 的替代建议。 该常量也已暴露到能力清单的 limits 里。新增 1 条测试（2**1000 连乘 20 次，约 6000 位）。

4　审查中确认无误的部分

以下内容通读后确认正确，可以放心：

  • 安全边界设计——AST 白名单 + generic_visit 默认拒绝 + 属性/下标访问整类禁用， 这三层配合是正确的。visit_Call 要求 func 必须是裸 ast.Name， 堵住了 a.b() 和 a[b]()，这个细节抓得很准。
  • 幂运算限额双路共用——** 运算符和 pow() 函数都走 _checked_pow， 没有留下单边绕过的口子。
  • 温度和数据的换算——摄氏/华氏/开尔文/兰氏的仿射变换系数正确 （212°F = 100°C、32°F = 0°C、0°C = 273.15K 均对）； 数据单位 1024 进制换算正确，且显式注明了进制。
  • 整数精度保护——_normalize_numeric 只处理 float， 2**100 保持 int 类型不丢精度，这条核心卖点是成立的。
  • 加载器的功能发现——_collect_feature_subclasses 用 mod_name.startswith(f"{namespace}.") 正确处理了"包 __init__.py 转出子模块类" 这个场景，并用 seen 集合去重，逻辑严密。
  • stdio 传输的日志隔离——setup_logging 强制写 stderr， 并在三处文档里反复提醒，这个最容易踩的坑防住了。
  • 架构的可扩展性承诺——test_architecture.py 里那条 "运行时创建新功能目录、验证无需改动既有文件"的回归测试，是真的在守这个承诺，设计得很好。
